## 1. 한 문장 정의

새록 심사단은 서비스 아이디어 한 줄을 받아 심사위원 3명의 평가, 핵심 가정 3개의 공개 근거 검증, 경쟁 서비스 조사, 가상 사용자 패널, 가격·수익 계산을 거쳐 `진행·조건부·보류` 판정과 다듬은 방향 2~3개(추천 하나)를 내는 검증 에이전트입니다. 기획서는 쓰지 않습니다.

## 2. 해결할 문제

혼자 기획하는 사람은 아이디어에 반대해 줄 사람이 없어, 경쟁 서비스와 쓸 사람의 반응을 확인하기 전에 만들기 시작합니다. 4번 새록 검토관은 PRD에 칸이 다 있는지만 보고 아이디어의 가치는 평가하지 않으므로(PRD v2.0 7장), PRD를 쓰기 전 단계가 비어 있습니다.

### 근거

사용자 본인 사례 1개(사용자 입력, 2026-10-17 프로젝트 기록으로 확인). 이미지 레퍼런스를 스타일 스펙으로 바꾸는 서비스 기획 Refspec이다.

- 2026-10-13: 기획을 시작하고 해결책부터 만들었다. 추출 프롬프트 2판, 색 추출 스크립트, 화면 시안 5장, 랜딩 페이지를 만들었다.
- 2026-10-14: 추출 품질 테스트는 통과했다. 하지만 사용자 인터뷰는 0명이었고, 신청 폼도 만들지 않았다.
- 그 뒤 경쟁 조사: 이미지를 프롬프트로 바꾸는 도구가 이미 10개 넘게 있었다. PRD에 적었던 '빈자리' 포지셔닝을 거둬들였다.
- 2026-10-15: "그냥 Claude에게 물어보면 된다"는 판단으로 프로젝트를 중단했다. 가장 큰 대체재가 범용 AI라는 사실은 시작 전 경쟁 조사 한 번으로 알 수 있었다.

이 사례에서 심사단 설계로 가져온 것은 두 가지다.

- 경쟁 조사와 '사람들이 지금 다른 방법으로 해결한다' 가정 검증을 만들기 전 단계에 둔다(4장 20번).
- 같은 기획에서 AI가 만든 가상 인터뷰 응답이 가설을 되풀이할 뿐이라 근거에서 뺐다. 그래서 가상 패널은 판정에 넣지 않는다(8장).

사례가 1개뿐이라 '혼자 기획하는 사람이 대부분 그렇다'는 일반화는 하지 않는다. 6장 지표로 아이디어 3개를 돌린 뒤 다시 본다.

## 3. 대상 사용자

새록이를 만드는 사용자 본인처럼 혼자서 기획부터 구현까지 하는 사람입니다. 취업 포트폴리오, 공모전, 개인 서비스 아이디어를 PRD로 옮기기 전에 걸러 보고 싶어 합니다.

## 5. 해결책: 검증 흐름

1. `/saerok-idea:judge <아이디어 한 줄>`을 입력합니다.
2. 4칸 중 빠진 것만 최대 3문항 묻고, 모르는 칸은 `미정`으로 둡니다.
3. 심사위원 3명이 각자 기준표로 1~5점과 투표, 이유를 냅니다.
4. 아이디어가 기대는 핵심 가정 3개를 뽑습니다. 심사위원이 가장 많이 걸고넘어진 지점을 우선합니다.
5. 패널 규모와 예상 사용량을 알리고, 가정 검증·경쟁 조사에 보낼 웹 검색어 목록(일반 낱말)을 보여 준 뒤 확인받습니다.
6. 심사단이 가정마다 공개 근거를 찾아 `받침`·`반박`·`확인 못 함`과 링크·확인 날짜를 적습니다. 근거가 없으면 `확인 못 함`으로 두고 지어내지 않습니다.
7. 경쟁 서비스를 검색해 이름·링크·확인 날짜·차이를 표로 만듭니다. 리뷰의 불만은 가정 검증 근거로도 씁니다.
8. 가상 사용자 패널이 쓸지 말지와 이유를 답합니다. 결과는 비율 예측이 아니라 반대 이유 모음으로 정리합니다.
9. 사용자가 준 가격·비용이 있으면 스크립트가 손익분기를 계산합니다.
10. 스크립트가 투표와 가정 검증 결과로 판정을 냅니다(4장 19번).
11. Claude가 판정에 맞춰 다듬은 방향 2~3개를 내고 하나를 추천합니다. 방향마다 해결하는 심사 지적·반박된 가정, 사용자가 직접 확인할 일(웹으로 확인 못 한 것만)을 붙입니다.
12. 결과를 `~/.saerok/idea/<아이디어>/<날짜>/verdict.md`에 저장합니다. 사용자가 방향을 고르면 `/saerok-idea:judge --from <verdict.md> --direction 2`로 그 방향을 다시 심사하거나, `/saerok-prd:design --from <verdict.md>`로 검토관에 넘깁니다.

## 6. 성공 지표

- 2026-11-30까지 아이디어 3개 이상을 심사단으로 돌린다.
- 가정 검증에서 `확인 못 함`이 아닌 결과(받침·반박)가 가정 3개 중 2개 이상인 심사가 절반 이상이면 검증이 제 몫을 한다고 본다. 아니면 근거 찾는 출처를 넓힌다.
- 제시한 방향 중 하나를 골라 다시 심사하거나 검토관으로 넘긴 비율이 50% 이상이면 방향이 쓸모 있다고 본다.
- 판정을 받고 방향을 바꾸거나 접은 아이디어가 1개 이상이면, 만들기 전에 문제를 잡은 것으로 본다.

## 7. 하지 않을 것

- 기획서·PRD 작성(4번 새록 검토관의 일)
- 실존 인물이나 유명 투자자 흉내
- 가상 사용자 패널 결과를 실제 수요나 구매 비율로 표현
- 투자·창업의 최종 판단(AGENT-SPEC 7번)

| 가정·위험 | 대응 |
|---|---|
| 심사위원과 패널이 모두 같은 Claude라 의견이 비슷하게 나온다 | 심사위원마다 기준표를 따로 주고, 패널은 페르소나 유형을 나눔. 반대 이유가 하나도 없으면 결과에 그 사실을 적음 |
| 시뮬레이션 결과가 실제 검증처럼 읽힌다 | 모든 패널 결과에 `AI 시뮬레이션` 표시, 비율 숫자를 판정 근거로 쓰지 않음. 판정에는 패널이 아니라 공개 근거로 한 가정 검증을 반영 |
| 여러 Claude를 돌려 사용량이 크다 | 기본 패널 20명, 시작 전 예상 사용량 안내, 단계별 다시 실행. 18번 파수꾼으로 실제 사용량을 확인 |
| 아이디어가 밖으로 새어 나갈 수 있다 | 파일은 홈 폴더에만 저장. 다만 분석은 Claude(Anthropic 서버)가 하고 웹 검색어는 검색 서비스로 나가므로 완전한 비공개는 아님을 README에 밝힘. 검색어는 일반 낱말로 만들고 확인받음 |
| 경쟁 조사가 놓친 서비스 때문에 판정이 틀린다 | 찾은 범위(검색어·날짜)를 함께 적고, 사용자가 아는 경쟁 서비스를 더할 수 있게 함 |
| 공개 근거가 아이디어를 받치는 쪽으로만 골라질 수 있다(확증 편향) | 가정마다 반박 근거를 먼저 찾게 하고, 받침과 반박이 함께 있으면 둘 다 적음. 반박 근거를 찾지 못한 사실도 기록 |
| 방향 제시가 결국 Claude의 아이디어로 원래 아이디어를 덮는다 | 방향은 제안일 뿐 원래 아이디어 기록은 덮어쓰지 않음(AGENT-SPEC 5번). 방향마다 무엇을 바꿨는지를 원래 입력과 나란히 보여 줌 |
| 웹 화면에서 API 키가 새어 나갈 수 있다 | 키는 그 브라우저에만 두고(기본은 탭을 닫으면 지워짐, '이 브라우저에 기억'을 고를 때만 남김), 새록이 서버로 보내지 않음. 화면은 외부 스크립트를 읽지 않음. 공용 PC에서는 쓰지 말라고 안내 |
| 판정 규칙이 너무 단순하다 | 첫 버전은 고정 규칙으로 같은 투표에 같은 판정을 보장하고, 아이디어 3개를 돌린 뒤 다시 봄 |

## 9. 완료 기준

- 플러그인 `saerok-idea`와 스킬 `/saerok-idea:judge`, 마켓플레이스 등록
- 판정 스크립트(투표·가정 검증 → 판정)와 손익분기 계산 스크립트, 텍스트·JSON 출력
- `~/.saerok/idea/` 저장과 날짜별 기록, 같은 아이디어 전후 비교
- 가정 검증 결과와 방향 2~3개를 담은 `verdict.md` 양식, 고른 방향 다시 심사(`--direction`)
- 검토관 `/saerok-prd:design --from <verdict.md>` 지원
- 예시 아이디어(`examples/`)와 판정 규칙·계산 자동 검사를 루트 `test_fruits.py`에 연결
- 10장의 버전 맞춤 스크립트·워크플로와 어긋남 검사
- 웹 화면(`web/`)을 GitHub Pages `/idea/`로 배포하고, 터미널 `saerok-idea`로 같은 화면을 내 PC에서 열기
- 화면 판정·기록·`verdict.md`가 Python과 같은지, 내 PC 서버의 접근 막기·동시 기록을 자동 검사
- 터미널 화면이 기본으로 내 Claude 구독(`claude -p`)을 쓰고, 설정에서 API 키 방식으로 바꾸기. 구독 응답 변환·실행 인자·API 키 제외를 자동 검사

## 10. 검토관 버전 따라가기

심사단 PRD는 검토관 PRD의 짝 문서입니다. 심사단은 판정을 검토관(`/saerok-prd:design --from`)에 넘기므로, 검토관 설계가 바뀌면 심사단 문서도 같은 버전에 맞춰 다시 봐야 합니다.

| 항목 | 규칙 |
|---|---|
| 파일 이름 | `docs/PRD-v<검토관 버전>-idea.md`. 지금은 검토관 v2.0이므로 `PRD-v2.0-idea.md` |
| 검토관 버전 찾기 | `docs/PRD-v*.md` 중 첫 줄이 `# 새록이 4번 열매 PRD`로 시작하는 파일의 가장 높은 버전. `-idea`가 붙은 파일은 제외 |
| 맞춤 스크립트 | `scripts/sync_idea_prd.py`. 버전이 다르면 `git mv`로 파일 이름을 바꾸고, 제목 줄의 버전, 머리말의 `문서 버전` 줄, `README.md`·`CLAUDE.md`·`AGENTS.md`의 링크를 새 이름으로 고침. 본문은 바꾸지 않음 |
| 자동 실행 | `.github/workflows/idea-prd-sync.yml`. `main`에 `docs/PRD-v*.md`가 바뀐 push가 오면 스크립트를 돌리고, 바뀐 것이 있으면 `chore: sync saerok-idea PRD`로 커밋·push(grow 봇과 같은 방식, `concurrency`로 겹침 방지) |
| 검사 | `sync_idea_prd.py --check`를 `test_fruits.py`에 연결. 버전이 어긋나거나 링크가 옛 이름을 가리키면 로컬 검사에서 바로 실패 |
| 연결 검사 | 검토관 `skills/design/SKILL.md`에 `--from` 안내가 없으면 검사 실패. 검토관이 바뀌어 연결이 끊긴 것을 이름 맞춤과 별개로 잡음 |
| 내용 다시 보기 | 버전이 바뀌면 머리말에 `검토관 vX로 이름만 맞춤, 내용 다시 보기 전` 표시를 남김. 사람이 내용을 확인한 뒤 지움. 자동으로 본문 결정을 바꾸지 않음(AGENT-SPEC 5번) |

| 가정·위험 | 대응 |
|---|---|
| 봇 커밋이 늘어 로컬과 원격이 자주 어긋난다 | 검토관 PRD가 바뀔 때만 돌고, 바뀐 것이 없으면 커밋하지 않음. 커밋 전 `git fetch` 규칙은 그대로 |
| 이름만 맞고 내용은 옛 검토관 기준으로 남는다 | '내용 다시 보기 전' 표시를 남겨 사람이 확인하게 함 |
| 검토관 PRD 첫 줄 형식이 바뀌면 버전을 못 찾는다 | 못 찾으면 바꾸지 않고 검사를 실패시켜 알림. 0이나 옛 값으로 대신하지 않음(AGENT-SPEC 3번) |
