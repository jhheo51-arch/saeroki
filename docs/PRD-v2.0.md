# 새록이 4번 열매 PRD v2.0: 새록 검토관

- 작성일: 2026-10-17
- 상태: 첫 버전 완성(🍎 열매, 2026-10-17). 8장 완료 기준을 모두 채움
- 대상: 4번 열매 `PRD 설계 지원`, 이름 `새록 검토관`, 명령 `saerok-prd`
- 실행 환경: 내 PC의 Claude Code 스킬(`/saerok-prd:design`·`/saerok-prd:review`)과 검사 명령
- 이전 문서: [PRD v1.9](PRD-v1.9.md), 원래 목록은 [PRD v01](PRD-v01.md)

## 1. 한 문장 정의

새록 검토관은 내가 쓴 PRD를 기준표 9개로 검사해 빠진 칸과 근거 없이 쓴 줄을 줄 번호로 짚고, 고칠 질문을 돌려주는 검토 에이전트입니다. PRD를 대신 써 주지 않습니다.

## 2. 해결할 문제

PRD를 쓰다 보면 해결책은 자세해지고 문제의 근거, 성공 지표, 틀릴 수 있는 가정은 빠지기 쉽습니다. "Claude에게 그냥 물어보면 된다"는 대안은 물을 때마다 짚는 곳이 달라, 고친 뒤 무엇이 나아졌는지 비교할 수 없습니다.

### 근거

2026-10-17 새록 검토관 첫 버전으로 이 저장소의 PRD 4개를 검사한 결과입니다.

| PRD | 기준 충족 | 빠진 기준 |
|---|---:|---|
| v01 제품군 | 5/7 | 하지 않을 것, 성공 지표 숫자 |
| v1.6 1번 콘텐츠 개인화 | 6/7 | 가정과 위험 |
| v1.8 16번 새록 SQL | 3/7 | 문제 근거, 성공 지표, 대상 사용자, 가정과 위험 |
| v1.9 18번 새록 파수꾼 | 4/7 | 성공 지표, 대상 사용자, 가정과 위험 |

위 표 기준으로 4개 중 3개에 가정과 위험이 없었고, 2개는 `완료 기준`(만들 목록)만 있고 만든 뒤 효과를 볼 지표가 없었습니다. 쓴 사람이 꼼꼼해도 같은 칸이 반복해서 빠집니다.

## 3. 대상 사용자

새록이를 만드는 사용자 본인처럼 혼자서 기획부터 구현까지 하는 사람입니다. 리뷰해 줄 동료가 없어 PRD의 빈 곳을 스스로 찾아야 합니다.

## 4. 확정 사항

| 번호 | 질문 | 결정 |
|---:|---|---|
| 1 | 무엇을 가장 잘하는가 | PRD 검토관. 버전 추적은 이번에 하지 않음(질문형 설계는 9번으로 추가) |
| 2 | 쓰는 방식 | Claude Code 스킬. 새록 파수꾼처럼 플러그인 `saerok-prd`로 설치 |
| 3 | 검사 방식 | 두 층. 규칙 검사(같은 PRD는 언제나 같은 결과)와 Claude 의견(AI 해석으로 따로 표시) |
| 4 | 기준표 | 해결할 문제, 문제의 근거, 성공 지표, 대상 사용자, 하지 않을 것, 가정과 위험, 해결책(기능), 해결안 선택, 측정과 회고(뒤의 둘은 10번에서 추가) |
| 5 | 줄 지적 | 순서(해결책이 문제보다 먼저), 모호(숫자 없는 '쉽게'·'많은' 등), 출처(문제 절의 숫자에 출처·날짜 없음), 정하지 않은 칸(`TBD`·`미정`) |
| 6 | 입력 | Markdown 파일 경로 또는 대화에 붙여 넣은 본문 |
| 7 | PRD 수정 | 하지 않음. 사용자가 요청하면 바꿀 문장을 먼저 보여 주고 확인받음 |
| 8 | 주제가 달라 기준이 안 맞을 때 | 기준 9개는 고정. 말이 다르면 프로젝트 설정(`.saerok-prd.json`)의 낱말로, 기준이 필요 없으면 이유를 밝힌 '해당 없음'으로 맞춤. 규칙이 주제를 짐작하지 않음 |
| 9 | 설계 단계 | 스무고개 스킬 `/saerok-prd:design`(2026-10-17 추가). 한 번에 하나, 최대 20개. 1~9번은 기준표를 채우는 질문, 10번부터 주제별 결정. 사용자가 고른 것만 확정 사항에 적고, 근거 숫자는 지어내지 않으며, 초안은 바로 `check`로 검사 |
| 10 | 흐름 기준(2026-10-22 추가) | 문제 정의 → 목표와 가설 → 해결안 선택 → 개발 → QA → 출시와 측정 → 결과 검토 → 다음 추진 흐름을 덮도록 기준에 해결안 선택과 측정과 회고를 더해 9개로 늘림. 바뀌는 정도가 목표면 기준선이 있어야 성공 지표가 있음, 측정과 회고는 언제 잴지가 있어야 있음. PRD는 출시 전 문서라 결과 자체는 보지 않음 |

## 5. 해결책: 검사 흐름

PRD를 쓰기 전에는 `/saerok-prd:design 만들 것`으로 스무고개를 해 '스무고개 확정 사항' 표와 PRD 초안을 만들고, 초안을 아래 2단계 검사로 넘깁니다.

1. `/saerok-prd:review <파일>`을 입력합니다.
2. 스킬이 `bin/saerok-prd check <파일> --json`을 실행합니다. 제목의 낱말로 절을 기준에 짝짓고, 본문 줄을 규칙으로 검사합니다.
3. Claude가 본문을 읽고 다섯 가지만 의견으로 더합니다: 문제가 해결책을 전제하는지, 근거가 문제를 받치는지, 지표가 문제와 이어지는지, 기준표가 제목만 보고 잘못 짝지은 곳이 있는지, 가설의 지표를 측정과 회고에서 그대로 재는지.
4. 기준표, 줄 지적, 검토관 의견(AI 해석), 고칠 질문 3~5개 순서로 답합니다.
5. PRD를 고친 뒤 `/saerok-prd:review 이전.md 이후.md`를 입력하면 `saerok-prd compare`가 기준별 전후 상태, 고친 지적과 새 지적, 고친 비율을 셉니다. 지적은 줄 번호 대신 종류와 원문으로 짝짓습니다.

## 6. 성공 지표

- 2026-10-31까지 새로 쓰거나 고치는 PRD 2개 이상을 검토관으로 검사하고, 고친 뒤 기준 충족 수가 검사 전보다 늘었는지 봅니다.
- 줄 지적 중 사용자가 실제로 고친 비율(`saerok-prd compare`의 고친 비율)이 50% 이상이면 지적이 쓸모 있다고 봅니다. 30% 아래면 규칙을 다시 봅니다.
- 기준표 오판(Claude 의견 4번이 바로잡은 수)을 기록해 제목 낱말 목록을 고칩니다.

## 7. 가정과 위험

| 가정·위험 | 대응 |
|---|---|
| PRD가 Markdown 제목(`##`)으로 절을 나눈다 | 아니면 기준표 9개 중 7개 이상이 '빠짐'으로 나옴. 스킬이 이 경우를 알려 줌 |
| 제목 낱말로 짝짓기는 오판이 있다(예: '사용자가 지정한 에이전트'를 대상 사용자로 봄) | Claude 의견에서 바로잡고, 규칙 결과는 고치지 않고 함께 보여 줌 |
| 기준을 다 채운 PRD가 좋은 PRD라고 오해할 수 있다 | 검토관은 칸이 있는지만 본다고 답마다 밝히고, 아이디어 평가는 하지 않음 |
| 주제마다 필요한 칸이 달라 기준 9개가 안 맞을 수 있다(쇼츠 기획, 공고 분석 등) | 이유를 밝힌 '해당 없음'은 분모에서 빼고, 낱말이 다르면 프로젝트 설정으로 더함. 이유 없는 해당 없음은 받지 않음 |
| '해당 없음'이 빈칸을 숨기는 구멍이 될 수 있다 | 이미 있는 절은 해당 없음으로 바꾸지 않고, 이유를 결과에 그대로 보여 줌. 비교 결과에서도 나아짐이 아니라 '해당 없음 바뀜'으로 따로 표시 |
| 스무고개 초안이 사용자의 결정이 아니라 Claude의 권장안으로 채워질 수 있다 | 권하는 보기는 권할 뿐이고 사용자가 고른 것만 적음. 모르는 칸은 `미정`으로 남기고 초안 검사에서 다시 짚음 |

## 8. 완료 기준

- `saerok-prd check`가 기준표 9개와 줄 지적 4종을 텍스트·JSON으로 출력
- 플러그인 스킬 `/saerok-prd:review`와 마켓플레이스 등록
- 허술한 예시 PRD(`examples/weak-prd.md`)와 자동 검사
- `saerok-prd compare`가 고치기 전후의 기준 변화, 고친 지적·새 지적, 고친 비율을 텍스트·JSON으로 출력(`--since`로 git 이전 버전, `--log`로 기록)
- 기준이 약한 경우(조사 계획만 있는 근거, 모두 풀린 질문, 빈 절)와 문서 경고(긴 문서, PRD가 아닐 수 있음)
- 주제별 대응: 프로젝트 설정의 제목 낱말과 이유를 밝힌 '해당 없음'
- 성공 지표는 단위 있는 목표 숫자가 있어야 '있음', `NEEDS CLARIFICATION` 표시를 정하지 않은 칸으로 지적
- 플러그인 스킬 `/saerok-prd:design`(설계 스무고개)과 스무고개 초안 예시(`examples/design-draft.md`, 기준 9개 충족을 자동 검사)
