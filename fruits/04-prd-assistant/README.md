# 🌸 4 새록 검토관 (PRD 설계 지원)

PRD를 쓰기 전에는 스무고개로 결정을 하나씩 확정하고, 쓴 뒤에는 기준표 7개로 검사해 빠진 칸과 근거 없이 쓴 줄을 줄 번호로 짚습니다. 결정을 대신 내리거나 근거를 지어내지 않습니다.

- 상태: 🍎 열매(첫 버전 완성, 2026-10-17)
- 설계: [PRD v2.0](../../docs/PRD-v2.0.md)
- 공통 원칙: [AGENT-SPEC.md](../../AGENT-SPEC.md)

## 설치

Claude Code 대화창에서:

```text
/plugin marketplace add jhheo51-arch/saeroki
/plugin install saerok-prd@saeroki
```

그다음 `/saerok-prd:review docs/내-PRD.md`처럼 PRD 파일을 넘기거나, PRD 본문을 붙여 넣고 `/saerok-prd:review`를 입력합니다. Python 3.10 이상이 필요합니다.

## 설계 단계: 스무고개

`/saerok-prd:design 만들 것 한두 문장`을 입력하면 질문을 하나씩(최대 20개) 던져 결정을 확정합니다.

- 1~7번은 기준표 7개를 채우는 질문입니다(대상 사용자 → 문제 → 근거 → 성공 지표 → 하지 않을 것 → 기능 → 위험). 방향이 틀리면 뒤의 결정이 모두 헛수고라 먼저 묻습니다.
- 8번부터는 실행 환경·데이터·화면처럼 주제마다 다른 결정을, 지금 정하지 않으면 만들 수 없는 것부터 묻습니다. 정할 것이 적으면 20개를 채우지 않습니다.
- 고를 수 있는 질문은 권하는 보기를 맨 앞에 두고, 근거 숫자처럼 지어내면 안 되는 답은 짧은 답으로 받습니다. 정하지 못한 것은 `미정`으로 남깁니다.
- 끝나면 '스무고개 확정 사항' 표와 PRD 초안을 만들고(파일은 확인받은 뒤), 바로 `check`로 검사해 빈 기준만 1~3개 더 묻습니다.
- 기존 PRD 경로를 함께 넘기면 검사에서 빠지거나 약한 기준과 `미정` 줄만 묻습니다.

초안 모양은 [`examples/design-draft.md`](examples/design-draft.md)에 있습니다(꾸며 낸 내용, 기준 7개 충족).

질문 한도와 보기 형식은 [github/spec-kit](https://github.com/github/spec-kit)의 `clarify`(질문 5개, 보기 2~5개, 영향 큰 것부터)를 참고했고, 한도는 새록이 PRD v1.6~v1.8에서 써 온 20개로 정했습니다.

## 무엇을 보나

검사는 두 층입니다. **규칙 검사**는 AI 없이 돌아서 같은 PRD는 언제나 같은 결과가 나오고, 고친 뒤 다시 돌리면 무엇이 나아졌는지 비교할 수 있습니다. 그 위에 **검토관 의견**은 Claude가 본문을 읽고 더하는 해석이라 따로 표시합니다.

### 기준표 7개

| 기준 | 있음으로 보는 때 |
|---|---|
| 해결할 문제 | 제목에 '문제'·'배경'이 든 절 |
| 문제의 근거 | '근거'·'조사'·'인터뷰' 절에 이미 확인한 숫자·날짜·출처가 있음(조사 계획만 있으면 약함), 또는 문제 절 안의 숫자·출처 |
| 성공 지표 | '성공'·'지표'·'목표' 절에 단위 있는 숫자(30%, 20명, 4주, 20/20)가 있음. 목록 번호·날짜·버전만 있으면 약함, `완료 기준`만 있으면 빠짐 |
| 대상 사용자 | '사용자'·'대상'·'독자'·'페르소나' 절('사용자 흐름'·'사용자 지정'처럼 기능을 뜻하는 제목은 뺌) |
| 하지 않을 것 | '범위 밖'·'비목표'·'하지 않'·'제외'·'보류' 절 |
| 가정과 위험 | '가정'·'위험'·'한계'·'열린 질문' 절(질문이 모두 풀렸으면 약함, '위험 신호'처럼 기능 이름은 뺌) |
| 해결책(기능) | '기능'·'요구사항'·'설계'·'화면'·'흐름' 절 |

'사용자와 목표'처럼 한 제목에 두 기준이 들어 있으면 두 기준 모두 있음으로 봅니다. 제목만 있고 내용이 없는 절은 약함입니다.

### 문서 경고

| 경고 | 나오는 때 |
|---|---|
| 긴 문서 | 500줄이 넘음. 표본에서 이보다 긴 PRD 2개는 모두 구현 기록이 섞여 있었습니다. |
| PRD가 아닐 수 있음 | 기준이 5개 이상 빠짐. PRD가 아니거나 `##` 제목으로 절을 나누지 않은 문서입니다. |

### 주제가 달라 기준이 맞지 않을 때

PRD는 주제마다 쓰는 말과 필요한 칸이 다릅니다. 기준 7개는 어떤 주제든 결정을 내리려면 필요한 칸이라 그대로 두고, 맞지 않는 곳만 직접 밝히게 합니다. 규칙이 알아서 주제를 짐작하지 않으므로 같은 PRD는 언제나 같은 결과가 나옵니다.

1. **말이 다를 때: 프로젝트 낱말.** 저장소 맨 위나 PRD 폴더에 `.saerok-prd.json`을 둡니다. PRD 폴더에서 위로 올라가며 찾고, git 저장소 맨 위에서 멈춥니다.

   ```json
   {"words": {"users": ["시청자"], "risk": ["팩트 체크"]}, "skip": {"metric": "1회성 발표 자료라 효과를 재지 않음"}}
   ```

2. **기준이 정말 필요 없을 때: 이유를 밝힌 해당 없음.** PRD 안에 주석으로 적습니다. 문서 안 주석이 설정 파일보다 우선합니다.

   ```markdown
   <!-- saerok-prd: 해당 없음 users 혼자 쓰는 도구라 사용자는 나 하나 -->
   ```

   이유가 없으면 받지 않고, 이미 있는 절은 해당 없음으로 바꾸지 않습니다. 해당 없음은 기준 수에서 빠져 `기준 6개 중 N개`처럼 나옵니다. 기준을 `users`로 적어도, `대상 사용자`로 적어도 됩니다.

3. **그래도 어긋날 때: 검토관 의견.** 제목은 맞는데 내용이 다른 절은 Claude가 의견 4번(기준표 오판)에서 짚고, 그 기록으로 기본 낱말 목록을 고칩니다.

### 줄 지적 4종

| 종류 | 짚는 것 |
|---|---|
| 순서 | 해결책 절이 문제 절보다 먼저 나옴 |
| 모호 | 문제·근거·지표 절에서 '쉽게'·'많은'·'개선' 같은 말이 숫자 없이 쓰임('개선 과제' 같은 이름과 부정문은 뺌) |
| 출처 | 문제·근거 절의 숫자에 출처나 잰 날짜가 없음(출처를 밝힌 문장 바로 아래 표는 그 출처를 따르고, '1회성' 같은 말은 숫자로 보지 않음) |
| 미정 | `TBD`·`TODO`·`미정`·`NEEDS CLARIFICATION`(spec-kit 표시)이 남아 있음 |

코드 블록과 `인라인 코드` 안의 말은 검사하지 않습니다.

### 검토관 의견(AI 해석)

문제가 해결책을 전제하는지, 근거가 문제를 받치는지, 지표가 문제와 이어지는지, 기준표가 제목만 보고 잘못 짝지은 곳이 있는지 네 가지만 봅니다. 아이디어가 좋은지는 평가하지 않습니다.

## 실제 PRD로 다듬기

2026-10-17 내 GitHub 저장소 22개에서 찾은 PRD 27개를 검사해 규칙 오판을 고쳤습니다. 줄 지적은 54개에서 19개로 줄었고, 제목을 못 알아봐 빠짐으로 잘못 본 기준 6곳을 바로잡았습니다. 이어서 반대 방향 오판도 고쳤습니다. '사용자 흐름'·'사용자 확인 항목'을 대상 사용자로 본 3곳과 질문이 모두 풀린 '열린 질문'을 위험으로 본 1곳을 각각 빠짐과 약함으로 바꿔, '있음'은 126개에서 122개가 됐습니다. 성공 지표는 목록 번호(`1.`)나 '375px'·'5종'만 있어도 통과하던 5곳을 단위 있는 목표 숫자가 없다는 이유로 약함으로 바꿔 '있음'이 117개가 됐습니다. 고친 뒤에도 가장 자주 빠진 기준은 가정과 위험(27개 중 18개), 하지 않을 것(13개), 문제의 근거(11개) 순이었습니다.

## 직접 실행

```bash
bash fruits/04-prd-assistant/bin/saerok-prd check fruits/04-prd-assistant/examples/weak-prd.md
```

`--json`을 붙이면 JSON으로, 경로 대신 `-`를 주면 표준 입력에서 읽습니다. [`examples/weak-prd.md`](examples/weak-prd.md)는 일부러 허술하게 쓴 예시라 기준 3개 충족, 줄 지적 5개가 나옵니다.

### 고치기 전후 비교

```bash
bash fruits/04-prd-assistant/bin/saerok-prd compare fruits/04-prd-assistant/examples/weak-prd.md fruits/04-prd-assistant/examples/weak-prd-revised.md
```

```text
기준 충족 3개 → 6개 (총 7개)
줄 지적 5개 → 2개: 고친 지적 3개(60%), 새 지적 0개
```

기준마다 전후 상태가 어떻게 바뀌었는지, 이전 지적 중 사라진 것과 새로 생긴 것을 보여 줍니다. 고치면 줄 번호가 밀리므로 지적은 종류와 원문(띄어쓰기 무시)으로 짝짓습니다. 그래서 문장을 고쳐 썼는데 같은 문제가 남아 있어도 '고친 지적'으로 셀 수 있습니다. 고친 비율은 [PRD v2.0](../../docs/PRD-v2.0.md) 성공 지표에 그대로 씁니다.

이전 파일을 따로 저장하지 않았으면 git에 남은 버전과 비교합니다. `--log`를 붙이면 날짜·파일·고친 비율이 JSON 한 줄씩 쌓여 성공 지표 기록으로 씁니다.

```bash
bash fruits/04-prd-assistant/bin/saerok-prd compare docs/PRD-v2.0.md --since HEAD~1 --log prd-log.jsonl
```

스킬에서는 `/saerok-prd:review 이전.md 이후.md`처럼 경로 두 개를 넘기거나, 경로 하나와 함께 "고친 거 비교해 줘"라고 합니다.
